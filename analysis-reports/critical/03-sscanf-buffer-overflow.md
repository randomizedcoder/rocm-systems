# Critical Analysis 03: sscanf/sprintf/fscanf/strcpy Buffer Overflow Risks in amdsmi

**Date:** 2026-04-11
**Component:** amdsmi (AMD System Management Interface)
**Branch:** basic-static-analysis
**Risk Category:** Buffer overflow via unbounded format-string operations
**Status:** 🟢 Fix submitted 2026-04-12 — [ROCm/rocm-systems#4941](https://github.com/ROCm/rocm-systems/pull/4941). PR also hardens the container-ID extraction in `fdinfo.cc` (previously silent 16-char truncation, unanchored `find()`, no charset validation) against CWE-20/78/117/120/190/400/626/1007 with a 69-test adversarial suite.

---

## Executive Summary

Multiple locations in amdsmi use `sscanf`, `sprintf`, `fscanf`, and `strcpy` without
proper width limits on `%s` format specifiers. While the input sources are almost
exclusively kernel sysfs/procfs files (not user-controlled network data), several
patterns could cause stack buffer overflows if kernel output is unexpectedly long or
malformed. The most concerning cases are `sprintf` into a 64-byte fixed buffer and
`strcpy` of a parsed container ID with no length bound.

## Detailed Findings

### Finding 1: sscanf with unbounded %s into 256-byte buffer (rocm_smi.cc:7146)

**File:** `projects/amdsmi/rocm_smi/src/rocm_smi.cc`
**Function:** `rsmi_event_notification_get` (RSMI_EVT_NOTIF_VMFAULT handler)

```cpp
// Line 7125: message is 256 bytes (MAX_EVENT_NOTIFICATION_MSG_SIZE)
char message[MAX_EVENT_NOTIFICATION_MSG_SIZE] = {0};  // 256 bytes

// Line 7143-7144: task_name is also 256 bytes
char task_name[MAX_EVENT_NOTIFICATION_MSG_SIZE];       // 256 bytes
memset(task_name, '\0', MAX_EVENT_NOTIFICATION_MSG_SIZE);

// Line 7146: No width limit on %s
sscanf(message, "%x:%s\n", &pid, task_name);
```

**Buffer:** `task_name` -- 256 bytes, stack-allocated.
**Input source:** `message` which itself was populated from `event_in` read via `fgets()` from
an anonymous pipe file descriptor. The pipe comes from the kernel's GPU event notification
subsystem. `fgets` limits `event_in` to 256 bytes, and `message` is a copy of it, so
`message` is at most 255 non-null characters.

**Assessment:** Since `message` is already bounded to 256 bytes by the earlier `fgets` call,
and `task_name` is the same size, the `%s` parse of a substring cannot exceed the source
length. **Low practical risk** -- the source buffer is the same size as the destination.
However, the missing width specifier is still a code-quality defect; a future refactor
changing buffer sizes could introduce a real overflow.

**Recommended fix:**
```cpp
// Replace:
sscanf(message, "%x:%s\n", &pid, task_name);
// With:
sscanf(message, "%x:%255s", &pid, task_name);
```

### Finding 3: fscanf with unbounded %s from sysfs file (amd_smi.cc:5478)

**File:** `projects/amdsmi/src/amd_smi/amd_smi.cc`
**Function:** `amdsmi_get_pcie_info` (or similar PCIe query)

```cpp
// Line 5448: buff is 256 bytes (AMDSMI_MAX_STRING_LENGTH)
char buff[AMDSMI_MAX_STRING_LENGTH];                   // 256 bytes

// Line 5478: Reads from /sys/class/drm/<card>/device/max_link_speed
if (fscanf(fp, "%lf %s", &pcie_speed, buff) != 2) {
```

**Buffer:** `buff` -- 256 bytes, stack-allocated.
**Input source:** sysfs file `/sys/class/drm/cardN/device/max_link_speed`. Kernel PCIe
subsystem generates this. Typical content is something like `16.0 GT/s` (9 characters).

**Assessment:** The sysfs file is generated by the kernel PCIe driver. Its content is
deterministic and short (under 20 characters). An attacker would need to control a
kernel module or compromise the kernel to alter this output. **Very low practical risk.**
Still a latent defect worth fixing.

**Recommended fix:**
```cpp
if (fscanf(fp, "%lf %255s", &pcie_speed, buff) != 2) {
```

### Finding 4: sscanf with unbounded %s into 10-byte buffer (amd_smi_utils.cc:356, 386)

**File:** `projects/amdsmi/src/amd_smi/amd_smi_utils.cc`
**Function:** `smi_amdgpu_get_ranges` (clock range parsing)

```cpp
// Line 324: str is only 10 bytes!
char str[10];

// Line 356: Parsing sysfs pp_od_clk_voltage
if (sscanf(line.c_str(), "%u: %d%s", &dpm_level, &freq, str) <= 2) {

// Line 386: Parsing sysfs pp_dpm_sclk/mclk
if (sscanf(line.c_str(), "%c: %d%s", &single_char, &sleep_freq, str) <= 2) {
```

**Buffer:** `str` -- **10 bytes only**, stack-allocated.
**Input source:** sysfs files `pp_od_clk_voltage` and `pp_dpm_sclk`/`pp_dpm_mclk`. These are
generated by the amdgpu kernel driver. Typical format is like `0: 500Mhz *` where `str`
would capture `Mhz` (3 chars) or `Mhz *` depending on parsing. The `%s` stops at
whitespace, so it captures tokens like `Mhz` or `GT/s`.

**Assessment:** Typical kernel output fits easily in 10 bytes. However, the buffer is
unusually small and there is no width specifier. If the kernel driver format changes or
a custom/modified driver produces longer tokens, this could overflow a 10-byte stack
buffer. **Moderate risk** due to the tiny buffer size making overflow easier to trigger
accidentally, even if not exploitable by a remote attacker.

**Recommended fix:**
```cpp
// Replace:
char str[10];
// ...
sscanf(line.c_str(), "%u: %d%s", &dpm_level, &freq, str)
sscanf(line.c_str(), "%c: %d%s", &single_char, &sleep_freq, str)

// With:
char str[10];
// ...
sscanf(line.c_str(), "%u: %d%9s", &dpm_level, &freq, str)
sscanf(line.c_str(), "%c: %d%9s", &single_char, &sleep_freq, str)
```

### Finding 5: sscanf with unbounded %s into 10-byte buffer (amd_smi_utils.cc:582, 585)

**File:** `projects/amdsmi/src/amd_smi/amd_smi_utils.cc`
**Function:** `smi_amdgpu_get_error_count` (RAS error count parsing)

```cpp
// str is declared as char str[10] (line 324, same function scope or nearby)
// Lines 582, 585:
sscanf(line.c_str(), "%s%ld", str, &(err_cnt->uncorrectable_count));
sscanf(line.c_str(), "%s%ld", str, &(err_cnt->correctable_count));
```

**Buffer:** `str` -- **10 bytes**, stack-allocated.
**Input source:** sysfs file `/sys/class/drm/<card>/device/ras/aca_umc` (or similar RAS
error file). Typical content is like `ue: 0` and `ce: 0` where the string token is
`ue:` or `ce:` (3 chars). However, the format could include labels like
`uncorrectable:` (14 chars) which would overflow the 10-byte buffer.

**Assessment:** This is the **most concerning sscanf case**. The `%s` has no width limit
and writes to a 10-byte buffer. The `str` variable is only used to skip the label, but
the label length depends on kernel driver output. If the RAS subsystem changes its label
format (e.g., `uncorrectable_errors: 5`), this would be a stack buffer overflow.
**Moderate-High risk** for the 10-byte buffer.

**Recommended fix:**
```cpp
// Option A: Add width specifier
sscanf(line.c_str(), "%9s%ld", str, &(err_cnt->uncorrectable_count));
sscanf(line.c_str(), "%9s%ld", str, &(err_cnt->correctable_count));

// Option B (better): Use C++ string parsing instead of sscanf
std::istringstream iss(line);
std::string label;
iss >> label >> err_cnt->uncorrectable_count;
```

### Finding 6: sscanf with unbounded %s into 13-byte buffer (fdinfo.cc:161)

**File:** `projects/amdsmi/src/amd_smi/fdinfo.cc`
**Function:** `gpuvsmi_pid_get_info` (fdinfo parsing)

```cpp
// Line 158: fd_bdf_str is only 13 bytes
char fd_bdf_str[13];

// Line 161: No width limit
if (sscanf(bdfline.c_str(), "drm-pdev:       %s", &fd_bdf_str[0]) != 1) continue;
```

**Buffer:** `fd_bdf_str` -- **13 bytes**, stack-allocated.
**Input source:** `/proc/<pid>/fdinfo/<fd>` files. The `drm-pdev:` line is generated by the
DRM kernel subsystem. A BDF (Bus:Device.Function) string is formatted as
`DDDD:BB:DD.F` which is exactly 12 characters + null terminator = 13 bytes.

**Assessment:** The 13-byte buffer is sized exactly for the expected BDF format. If the
kernel ever outputs a longer BDF representation (unlikely but possible with extended
domains), this overflows. The `strncmp` on line 165 limits comparison to 13 bytes but
the overflow has already happened in `sscanf`. **Moderate risk** due to the tight fit.

**Recommended fix:**
```cpp
if (sscanf(bdfline.c_str(), "drm-pdev:       %12s", &fd_bdf_str[0]) != 1) continue;
```

**File:** `projects/amdsmi/src/amd_smi/fdinfo.cc`
**Function:** `gpuvsmi_pid_get_info`

// Lines 171, 176, 181, 186, 190: All read integers with PRIu64 format
if (sscanf(line.c_str(), "drm-memory-gtt:  %" PRIu64, &mem) != 1) continue;

**Assessment:** These parse integers, not strings. Integer format specifiers like `%lu`

### Finding 8: strcpy without bounds check (fdinfo.cc:219)

**File:** `projects/amdsmi/src/amd_smi/fdinfo.cc`
**Function:** `gpuvsmi_pid_get_info`

```cpp
// Line 219: Unbounded strcpy into container_name
strcpy(info.container_name, container_id.c_str());
```

Where `info.container_name` is declared as:
```cpp
// In amdsmi.h:1349
char container_name[AMDSMI_MAX_STRING_LENGTH];  // 256 bytes
```

And `container_id` is:
```cpp
// Line 217-218:
container_id =
    line.substr(line.find(container_type_name[i]) + strlen(container_type_name[i]) + 1, 16);
```

**Buffer:** `container_name` -- 256 bytes, embedded in struct.
**Input source:** `/proc/<pid>/cgroup`. The `container_id` is extracted via `substr(..., 16)`
which limits it to 16 characters maximum.

**Assessment:** The `substr` call with length 16 ensures `container_id` is at most 16 chars,
well within the 256-byte buffer. **No practical overflow risk.** However, `strcpy` is still
a code smell; `strncpy` or `snprintf` would be more defensive.

**Recommended fix:**
```cpp
strncpy(info.container_name, container_id.c_str(), AMDSMI_MAX_STRING_LENGTH - 1);
info.container_name[AMDSMI_MAX_STRING_LENGTH - 1] = '\0';
```

### Finding 9: sprintf into 64-byte fixed buffer (rocm_smi_binary_parser.cc:82, 84, 198-206)

**File:** `projects/amdsmi/rocm_smi/src/rocm_smi_binary_parser.cc`
**Function:** `present_table` and `present_pmmetrics`

```cpp
// rsmi_name_value_t.name is char[64] (MAX_RSMI_NAME_LENGTH = 64)

// Line 82: Simple field name copy
sprintf((*kv)[*kvnum].name, "%s", table[x].field_name);

// Line 84: Field name with array index
sprintf((*kv)[*kvnum].name, "%s[%d]", table[x].field_name, y);

// Lines 198-206 (present_pmmetrics): Appending to name buffer progressively
sprintf((*kv)[*kvnum].name, "%s", table[x].field_name);
if (table[x].field_arr_size > 1) {
    sprintf((*kv)[*kvnum].name + strlen((*kv)[*kvnum].name), "[%" PRId64 "]", y);
}
if (x >= instance_start)
    sprintf((*kv)[*kvnum].name + strlen((*kv)[*kvnum].name), ".instance[%" PRId64 "]",
            cur_instance);
if (x >= smn_start)
    sprintf((*kv)[*kvnum].name + strlen((*kv)[*kvnum].name), ".smn[%" PRId64 "]", cur_smn);
```

**Buffer:** `(*kv)[*kvnum].name` -- **64 bytes** (`MAX_RSMI_NAME_LENGTH`).
**Input source:** `table[x].field_name` comes from compiled-in binary parsing tables that
describe PM metrics fields. The field names are derived from firmware/driver header
definitions.

**Assessment:** This is the **highest-risk pattern in this analysis**. Lines 198-206
progressively append to a 64-byte buffer without any length checking:
- First write: `field_name` (could be 30+ chars for some metrics)
- Second append: `[<index>]` (up to ~22 chars for large int64 values)
- Third append: `.instance[<value>]` (up to ~30 chars)
- Fourth append: `.smn[<value>]` (up to ~25 chars)

Total possible: 30 + 22 + 30 + 25 = **107 bytes into a 64-byte buffer**.

Even with typical short field names and small indices, the cumulative appends can
easily exceed 64 bytes. The field names come from firmware table definitions which
could change across GPU generations.

**Recommended fix:**
```cpp
// Replace all sprintf calls in present_pmmetrics with snprintf:
snprintf((*kv)[*kvnum].name, MAX_RSMI_NAME_LENGTH, "%s", table[x].field_name);
if (table[x].field_arr_size > 1) {
    size_t cur_len = strlen((*kv)[*kvnum].name);
    snprintf((*kv)[*kvnum].name + cur_len,
             MAX_RSMI_NAME_LENGTH - cur_len,
             "[%" PRId64 "]", y);
}
if (x >= instance_start) {
    size_t cur_len = strlen((*kv)[*kvnum].name);
    snprintf((*kv)[*kvnum].name + cur_len,
             MAX_RSMI_NAME_LENGTH - cur_len,
             ".instance[%" PRId64 "]", cur_instance);
}
if (x >= smn_start) {
    size_t cur_len = strlen((*kv)[*kvnum].name);
    snprintf((*kv)[*kvnum].name + cur_len,
             MAX_RSMI_NAME_LENGTH - cur_len,
             ".smn[%" PRId64 "]", cur_smn);
}

// Similarly for present_table (lines 82, 84):
snprintf((*kv)[*kvnum].name, MAX_RSMI_NAME_LENGTH, "%s", table[x].field_name);
// and:
snprintf((*kv)[*kvnum].name, MAX_RSMI_NAME_LENGTH, "%s[%d]", table[x].field_name, y);
```

## Exploitability Assessment

### Attack Surface Analysis

1. **Is amdsmi a library or a daemon?**
   amdsmi is a **shared library** (`libamd_smi.so`, `librocm_smi64.so`) loaded into
   user-space processes. It is NOT a network-facing daemon. It is used by monitoring
   tools like `amd-smi` CLI, ROCm profilers, and GPU management applications.

2. **Can an attacker control the input data?**
   - **sysfs files** (`/sys/class/drm/...`): Generated by the kernel amdgpu driver.
     Requires root or kernel compromise to modify. Not user-controllable.
   - **procfs files** (`/proc/<pid>/fdinfo/...`, `/proc/<pid>/cgroup`): Generated by
     the kernel. Process fdinfo requires appropriate permissions to read. Content
     format is determined by the kernel, not by the target process.
   - **Event notification pipe**: Kernel-generated GPU events. Not user-controllable.
   - **Binary firmware tables**: Compiled-in or loaded from firmware blobs. The field
     names in the parsing tables are fixed at compile time.

3. **Typical string lengths from sysfs:**
   - PCIe speed: `"16.0 GT/s"` (9 chars)
   - BDF string: `"0000:03:00.0"` (12 chars)
   - Clock frequency line: `"0: 500Mhz *"` (tokens are 3-6 chars)
   - RAS error labels: `"ue:"` or `"ce:"` (3 chars)
   - Task names: typically under 16 chars (TASK_COMM_LEN = 16 in Linux)

4. **Stack protection mitigations:**
   - **Stack canaries**: Enabled by default in modern GCC/Clang (`-fstack-protector-strong`).
     A stack buffer overflow would trigger `__stack_chk_fail` and abort, rather than
     allowing code execution.
   - **ASLR**: Enabled on all modern Linux distributions. Makes ROP gadget addresses
     unpredictable.
   - **NX bit**: Stack is non-executable on all modern x86-64 systems.
   - **FORTIFY_SOURCE**: If compiled with `-D_FORTIFY_SOURCE=2` (common in release
     builds), some `sprintf`/`strcpy` calls are replaced with bounds-checked versions
     at compile time.

5. **Impact of overflow:**
   - Most likely: process crash (stack canary detection or segfault)
   - Remote code execution: extremely unlikely due to ASLR + NX + canaries + the
     fact that input data comes from kernel, not network
   - Denial of service: possible if a monitoring tool crashes, but the GPU itself
     continues to operate normally

### Honest Threat Model

The realistic threat scenario is **not a malicious attacker** but rather:
- A **new GPU generation** with longer field names in PM metrics tables overflowing
  the 64-byte `rsmi_name_value_t.name` buffer (Finding 9)
- A **kernel driver update** changing sysfs output format, producing longer tokens
  that overflow the 10-byte `str` buffer (Findings 4-5)
- A **corrupted sysfs file** (hardware error or driver bug) producing unexpected output

These are reliability/robustness bugs, not security vulnerabilities in the traditional sense.

### Overall Real-World Severity: **Medium**

The `sprintf` chain in `rocm_smi_binary_parser.cc` (Finding 9) is a genuine buffer
overflow waiting to happen as new GPU generations add longer metric names. The 10-byte
buffer cases (Findings 4-5) are fragile. None of these are remotely exploitable by an
external attacker, but they represent real crash risks that could affect production
monitoring stability.
